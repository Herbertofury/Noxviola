# Tab Collections: full parity goal, measured first implementation

## Product goal and status
Premium local tab collection manager in both the sidebar and full browser view, ultimately matching and exceeding OneTab and comparable tab managers. Huge libraries must stay compact, searchable, durable and responsive. There is no stored-record cap, but disk, memory, response budgets and hardware are finite. Never advertise unlimited crash immunity. Status: **partial implementation; not full parity or release qualification**.

The live browser now calls a Rust helper with bundled SQLite. Save current workspace HTTP(S) tabs belonging to the current identity; pinned tabs are opt-in. Save-only and durable-save-then-close are separate actions. URL/title/pin collection semantics are explicit: this is not preservation of page history, unsaved forms, cookies or arbitrary session state. A tab that navigated, moved workspace/group, or changed saved metadata during the transaction is retained. Internal/extension pages are not silently claimed as saved. Restore one tab retains the saved record. Identity changes during restore abort activation.

Both surfaces browse collections and their tabs, search within a collection using token prefixes, import OneTab URL/title text, star/lock and archive/unarchive collections. Archived data is retained; no destructive cleanup is implemented. Current import text becomes one collection; source blank-line grouping is not yet preserved. No auto sync, tracking or network requests occur for saved links; no remote favicon fetching.

## Storage and transport
- SQLite WAL, synchronous FULL, foreign keys, transaction rollback, version check, explicit errors instead of resetting unknown/corrupt data. Unix database and sidecars restrict access to the owner. Desktop OS account protection still matters; this is not encryption at rest.
- Indexed identity/collection/keyset pages; FTS5 title/URL token-prefix search. SQLite page cache budget 8MiB; real process overhead exceeds it. No whole-library JSON rewrite or renderer hydration.
- Responses bounded by both rows (50 collections/100 tabs) and approximately 1MiB encoded data, with continuation cursors and no discarded matches. UI replaces pages instead of accumulating cards.
- Per-operation IPC budget 8MiB, no permanent collection-count limit. Larger import transactions must currently be split explicitly; streaming import into a single collection remains open. One operation runs at a time; simultaneous surfaces may receive an explicit busy error, not silent queuing.
- Writes report success only after SQLite commit. Abrupt termination never triggers automatic retry of an uncertain mutation. No live tabs close on transport/storage failure.

## Primary-source comparison and code study (2026-11-17)
- [OneTab official help](https://www.one-tab.com/help): current scope includes folders, quick access, tasks/stars, multi-selection, reordering/merging, sharing, omnibox search, shortcuts and opt-in private tabs. It also describes encrypted sync/backup. These remain acceptance requirements, not an outdated small group-list-only target. Proprietary internals were not available or claimed inspected.
- [Session Buddy](https://sessionbuddy.com/): compare contextual restoration, historical recovery, duplicates, advanced filtering and multi-format interchange. These are parity obligations, not implemented claims.
- [Tab Session Manager source](https://github.com/sienori/Tab-Session-Manager/tree/113b272d6b5a2159f50181d1771163c20381ad6c): inspected `src/background/sessions.js` (IndexedDB openCursor accumulation in getAll) and `src/background/search.js` (loads id/windows for all sessions before constructing search info). This implementation deliberately uses indexed database queries and bounded transfer instead. No third-party implementation copied.
- [SQLite durability](https://www.sqlite.org/pragma.html#pragma_synchronous) and [Electron ASAR executable limits](https://www.electronjs.org/docs/latest/tutorial/asar-archives): helper is explicitly unpacked and launched from app.asar.unpacked, not spawned from inside the archive.

## Follow-on: folders and precise collection reordering
Schema2 adds flat named folders, folder/collection rename, moving collections between root and folders, and placing a collection immediately before another or at the end. These are available on both surfaces through explicit Move / reorder, Place before, Folders, Root and Move here actions. Stable tab/collection IDs and content are unchanged. Locked collections cannot be moved or renamed until unlocked. Folder deletion and nesting, tab-level reordering and drag/drop remain open; these are not silently claimed implemented.

The version1→2 migration is transactional. Tests retain legacy rows/flags and deliberately introduce a schema conflict to prove rollback leaves version1 and its original columns intact. Ordered keyset cursors include an identity-scoped revision from the same read snapshot; mutations make stale cursors fail visibly with a First page recovery action rather than skipping/duplicating records. Ordering uses sparse numeric ranks and an in-database transactional rebalance when precision or equal neighbor ranks would prevent exact placement. Independent review reproduced an archive/unarchive equal-rank edge case and lost rename drafts; both corrected with regressions. Inline unsaved rename drafts are retained per identity/record.

The [large-folder fixture](evidence/tab-collection-folders-20261117.json) created and browsed 20,000 collections and 2,000 folders without loss, at most50 cards/page; indexed reorder retained all tabs. The [schema2 million-tab rerun](evidence/tab-collections-million-folders-20261117.json) verified integrity/restart and bounded deep pages. These are synthetic local measurements, not native runtime benchmarks. New source tests total504 and Rust tests2 pass; new packaged-browser feature-specific tests cover both surfaces, folders, bounded pages, real tab activation and process restart, pending hosted results at this checkpoint.

At the folder checkpoint bulk lazy restore was still next (implemented below as durable paged sessions), not disguised as eager opening: the existing browser still serializes open-tab arrays and creates tab DOM. That causal path must be made safe before claiming enormous libraries can all be restored smoothly.

## Follow-on: durable lazy restore sessions (schema3)
“Restore all lazily” now commits a durable session referencing **every** immutable source tab. Both sidebar and full library expose Lazy restore sessions and bounded, 50-row/1MiB pages. Creating the session does not insert placeholders into the host tab array, serialize them into browser state/session JSON, construct tab DOM, or load remote pages. Selecting Activate lazy tab materializes only that row as an ordinary browser tab. This deliberately is **not** “a million ordinary strip tabs already open.” General live-tab-array/strip virtualization remains open; enormous live workloads still need that host redesign.

Session creation freezes the collection count and high-water source ID in one SQLite transaction; source rows remain immutable and foreign-key-retained. Pause prevents further activations without deleting source or progress; Resume is explicit. Sparse stable browser-tab IDs are committed before activation. New and existing-tab retry paths await session persistence, so a failed write cannot be reported as durable success. A crash between claim, browser creation and session flush leaves the source/claim retryable; an already-live stable ID is focused rather than duplicated. There is no automatic ambiguous retry or network replay after restart. A previously requested label is not an assertion that navigation or persistence succeeded.

Identity and workspace are checked around storage awaits. A moved live tab is not duplicated into another workspace. Removing a workspace remains independent of optional collection storage: dormant sessions keep their original workspace ID and stay visible/recoverable, but refuse activation there until the user explicitly moves the session into a current workspace. The session does not silently migrate to default. UI completions from an old identity cannot install old titles/session IDs into a newer view.

The [million-tab lazy fixture](evidence/lazy-restore-million-20261117.json) created a durable snapshot in 7.66ms, enumerated all 1,000,000 rows across 20,000 bounded pages, and retained a stable activation claim across abrupt helper termination. These are synthetic local fixture measurements (parent RSS excludes helper), not native load-time, power-loss or unlimited-capacity guarantees. Source fixture is smaller/different than earlier million-tab measurements, so file sizes are not a compression comparison. Native packaged tests additionally assert bulk creation adds zero host tabs, activation adds exactly one, retry adds none, and restart retains the lazy session. Hosted acceptance is pending at this code checkpoint.

Remaining bulk parity: strip-integrated virtual dormant tabs, progressive multi-selected activation with concurrency/cancel policy, context/group preservation, explicit cleanup/delete options, and disk-full/power-loss/multi-instance fault tests. No full OneTab parity claim.

## Follow-on: whole-library search
Both surfaces now offer **Search entire library**: identity-scoped token-prefix search across saved titles/URLs in all folders, with explicit Live collections / Archived collections / Live and archived and Starred collections only filters. Results retain their source collection/folder, archive/star flags, an open-without-delete action and Browse source collection. Empty input yields no results and asks for a query; it does not load the entire library. This is not arbitrary substring matching, collection-name search or omnibox integration.

The Rust helper returns at most50 rows and approximately1MiB encoded data per page. Cursors bind identity, normalized query, archive/star filters and the library metadata revision inside one read transaction. A changed query/filter or renamed/moved/archived source invalidates an old cursor instead of silently mixing results. The UI keeps submitted search terms/filters separate from an edited draft, supports Enter, and suppresses old-identity responses. Source tabs and lazy restore claims are never modified by search.

A million-row stress run caught an important causal performance issue: bundled SQLite could reorder an implicit join into repeated FTS scans and hit the120second helper deadline. Explicit FTS-first CROSS JOIN plus direct FTS rowid range/order removed that plan and its match-wide sort without dropping records. An eligible-collection preflight makes an empty identity/scope cheap. [Final real-helper fixture](evidence/global-search-million-20261117.json): deep50row p50~35ms/p95~76ms, rare match0.89ms, empty identity0.15ms,17starred matches after1m unstarred rows~208ms; integrityOK. Sparse filters still traverse matching candidates and are not a constant-time guarantee. Parent RSS excludes helper. The script uses only a generated synthetic database and adds17synthetic starred rows after the million-row deep-page phase.

509 portable tests,2 Rust tests and120 source syntax files pass at this checkpoint. Packaged Windows/Linux search UI, provenance, Next and Browse source collection tests are added; hosted results pending. Full advanced search syntax, omnibox, saved queries, annotations/tasks and remaining parity stay open.

## Follow-on: streaming library-only backup and additive restore
Both surfaces expose **Library-only backup and additive restore**, using native file pickers. Export includes every folder (including empty folders), live/archived collection, saved URL/title/pin, star/lock/archive flag, relative ordering within each folder/archive view, and imported collection source provenance for the selected identity. Other identities are excluded. **It is plaintext**, not encrypted, and excludes browser cookies, credentials, live tabs/page state and lazy-session activation claims. Existing lazy sessions remain unchanged by import. This is a Noxviola `.noxlibrary` round-trip format, not yet the full OneTab/CSV/HTML export matrix.

Rust streams versioned newline-delimited records from one SQLite read snapshot. The final SHA-256/count footer covers the exact preceding bytes; it detects corruption/truncation, not the authenticity of whoever supplied the file. Exclusive0600 staging plus fsync and atomic no-clobber hard-link publication prevent replacing an existing backup or publishing a partial final file. Choose a new filename. Unsupported hard-link filesystems fail safely. A post-publication cleanup/sync failure explicitly tells the user the final backup may exist; cancellation may leave a uniquely named `.partial` staging file, never silently deletes unrelated files, and needs review before retry.

Import accepts only the same identity and supported format. Bounded1MiB lines, strict field/type parsing, duplicate ID/JSON field rejection, HTTP(S)-without-credentials validation, cross-reference/order validation, checksum/count verification and final EOF are checked before one additive transaction commits. SQLite file-backed TEMP tables remap IDs without loading the library into JavaScript; original collections/folders/tabs and lazy restore claims are never replaced. A persistent completion marker in that same transaction prevents retrying the same backup UUID from adding duplicate copies, including commit-before-response interruptions. A distinct newly exported backup can still add copies; there is no heuristic URL deduplication or destructive merge.

A dedicated helper performs streaming jobs without the interactive helper's120second timeout. SQLite still serializes writers, so concurrent mutations can report busy; ordinary reads use snapshots. Cancel stops the worker, but cancellation is not proof that a just-completed import never committed. The UI and close-time native prompt say to inspect the library first; same-backup completion markers make retries safe. Closing offers Keep browser open or Cancel backup and close before waiting for outstanding work. Status describes the operation, not fabricated percentage progress; per-record progress reporting remains open.

Tests cover metadata/provenance round-trip, other-identity exclusion, unchanged prior backup bytes, malformed/truncated/trailing/duplicate/unsafe input rollback, same-backup retry rejection, dedicated cancellation, trusted picker-only paths and reachable close handling. [Million-row fixture](evidence/library-backup-million-20261117.json) checks streaming checksum, every imported tab, retained existing data, interrupted export publication and interrupted import rollback. Timing/RSS are synthetic local measurements (parent excludes helper), not power-loss/disk-full guarantees. Native source-app tests drive the real picker-bound commands with explicitly supplied picker responses; packaged tests exercise the exact bundled helper and backup adapter. Native OS picker UI itself is not qualified by those fixtures.

Remaining backup work: encrypted/compressed variants, per-record progress, automated retention/recovery UI, disk-full/power-loss/multi-instance contention testing, full live-context/lazy-session migration, explicit merge/duplicate policies and cross-product formats.
