# Privacy and account boundaries

- Browser sessions use named persistent Electron partitions. The recorded source-app fixtures verify five site stores across two synthetic identities and restart on Windows/Linux; broader website/account and owner-profile qualification remains open. Avoid sensitive real accounts in the preview.
- Local favorites and account inventory are **plaintext metadata** in the per-user application-data directory. They are not an encrypted vault. Backups can contain names, handles, URLs and notes; keep them private.
- The account atlas accepts only metadata. It does not save passwords, tokens, cookies, TOTP secrets or recovery codes. Password-manager checkboxes are owner-maintained tracking markers, not proof of storage or integration. Do not enter secrets into any text field.
- No automatic cloud sync, account creation or credential import. Vault JSON import/export is explicit and local, with validation and reviewed merge behavior. The app-wide favorites library is shared across browser identities, not a separate confidential store for each identity.
- Public source contains synthetic test records only. The owner's offline account atlas inspired requirements; its records and files are not distributed.
- Site permissions default to deny until explicit consent. Decisions are keyed by identity, requesting origin, embedding origin and permission; camera and microphone are separate. Allow-once decisions are tied to the document, while durable allow/block decisions remain local and can be reviewed, revoked or reset. Navigation/disposal cancels unanswered requests, and failed persistence cannot produce a durable grant. Native OS behavior and the effect on already-running capture still require acceptance.
- Device and screen capture require real source/device pickers and are currently denied. Opaque/insecure/non-web origins are denied, with HTTP loopback exceptions for local web development. Extension-origin pages require a future authenticated extension-specific permission path; install consent does not imply device consent. There is no certificate-warning bypass, sandbox disabling or privileged remote-page bridge.
- Extension package inspection and local installation require explicit permission and identity review. Owned package digests protect the accepted bytes; they do not establish publisher identity. CRX remains blocked pending trust verification, and XPI/ZIP imports disclose unsigned trust. Source profiles, cookies, credentials and confidential extension settings are not silently migrated. See [the extension boundary](EXTENSION-ARCHITECTURE.md).
- The permission ledger, vault, account atlas and sessions use private local checkpoint files and preserve recovery evidence. These are plaintext records, not encrypted backups. A corrupt or unsupported permission checkpoint does not silently restore earlier allows; recovery requires an explicit action.
- History and bookmark trees are local and identity-scoped. Recording defaults to enabled with no hidden record-count or age limit; each identity can turn it off or choose an explicit retention interval. Removing entries changes the active list while preceding recovery checkpoints can retain older records. This is not forensic erasure. Workspace/group organization is shared and does not change a tab's cookie or extension identity.
- Download history is local, plaintext and app-wide with identity labels. It contains source URLs (which can include sensitive query parameters), filenames, destinations and transfer times. Metadata removal keeps downloaded files; previous/recovery checkpoints can retain older records. Restoring history never retries a URL or resumes a transfer automatically. See [the download lifecycle and recovery boundary](DOWNLOADS.md).
- Browser-host extension APIs authenticate the actual native extension frame or worker and exact Session. Named permissions and host grants apply to protected APIs, URL metadata and cookies; disable/uninstall revokes the enrollment even when a native unload fails. A loading/unloading error remains visible. Compatibility does not imply all requested APIs, platform components or marketplace signatures are supported.
- Appearance/shortcut presets export supported preference fields only; they exclude identities, history, bookmarks, accounts and extension grants. A custom search template or home address is used only through the user's browsing actions. The resource monitor performs explicit local samples and creates no polling service or telemetry endpoint.
- The packaged acceptance harness records finite synthetic/public-page Chromium NetLog and selected renderer network events under disposable profiles. Request bodies, headers and query values are not collected by its CDP recorder; default NetLog is retained separately with its own engine semantics. The results must distinguish site traffic, upstream services and first-party activity, and cannot establish absence of all traffic on every workload.
- Zero first-party telemetry is the accepted target. Source review and the absence of a telemetry implementation do not replace runtime network verification. Site traffic, user-selected services, runtime components and update/dictionary activity must be attributed in the actual network audit before G007 is accepted.
- The finite packaged `0e8601a` workflow records an actual Linux spellcheck dictionary GET from the Chromium CDN (`redirector.gvt1.com/edgedl/chrome/dict/en-us-10-1.bdic`), its redirect and HTTP 200 response. This engine request is absent from the page-target CDP counter. It is a dictionary download, not evidence of telemetry. Both platforms also record MDN-initiated POSTs to `incoming.telemetry.mozilla.org` while deliberately visiting MDN; the native initiator and CDP script/Ping attribution identify website traffic. These observations do not establish a universal absence of first-party traffic. The Windows failed restart's NetLog is incomplete JSON and its complete counts remain unknown. See [the exact failed run](https://github.com/Herbertofury/Noxviola/actions/runs/43777321374) and [checkpoint limits](CHECKPOINT-2026-11-15.md).
- The local spelling setting controls checks and correction suggestions across application-owned sessions. It preserves the prior enabled default and is excluded from appearance presets. It **does not constitute dictionary-download consent or a network opt-out**: the pinned [Electron Session constructor](https://github.com/electron/electron/blob/v44.11.3/shell/browser/api/electron_api_session.cc) initializes dictionaries before the post-creation enabled setter, and [Chromium dictionary loading](https://github.com/chromium/chromium/blob/152.0.7977.169/chrome/browser/spellchecker/spellcheck_hunspell_dictionary.cc) can fetch a missing dictionary independently of that enabled preference. No supported pre-session downloader-disable mechanism was established in this review. That requirement remains open; no dummy download URL, interception workaround, vendor preference rewrite or unsupported command-line flag is claimed as its solution.
- The separate Passwords tool encrypts usernames, origins and passwords with Electron safeStorage. Windows protection is tied to the signed-in OS account. The application lock clears the in-app password view, and autofill requires an explicit action in the matching identity and exact website origin. Profile backups and other processes with the same OS credentials remain within the OS-account trust boundary. See [sidebar services](SIDEBAR-SERVICES.md).
