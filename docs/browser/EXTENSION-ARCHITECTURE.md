# Extension management and compatibility checkpoint

Reviewed 2026-11-16 against the preserved Electron **44.11.3** baseline and pinned **45.3.2 candidate**, `yauzl` **3.4.0**, and PR #5. At exact 33d0, complete core/source/package and generated 44→45 migration passed on both hosts, including native local/sync isolation/events/quota/restart. The unchanged real package darkens the page but fails its popup file-access query; the next repair and managed-storage checks require fresh native receipts. Universal functionality and full package compatibility remain open.

## Implemented boundary

`browser/extensions.cjs` is the canonical package and lifecycle service. Production injects `browser/extension-runtime.cjs` over the real identity `Session.extensions` object; Node contract tests substitute only the native event/adapter boundary. The raw loader default exists for those isolated contract adapters; the desktop shell must inject `createExtensionLoader`. Package source bytes are not rewritten. Production additionally attaches the authenticated browser-host bridge described below, including a pinned Mozilla Promise facade in extension documents. Neither service contacts marketplaces, requests updates or transmits package inventories.

| Workflow | Behavior |
| --- | --- |
| Inspect unpacked directory | Copies regular files into an owned preview, preserves their bytes and case, rejects links/special files and ambiguous portable paths, parses the manifest, lists declared permissions and content-script match patterns, and detects dotted API references without executing the package. |
| Inspect ZIP | Uses the maintained ZIP parser with lazy entry streaming, size verification, additional CRC verification, path/collision checks and available-disk checks. A single enclosing directory may be removed. No source code or manifest is rewritten. |
| Inspect XPI | Uses the same safe package inspection, explicitly labels publisher/signature trust as unverified, retains signature metadata, and requires acceptance as an unsigned local import. This does not validate a Mozilla signature or confer Firefox store trust. |
| Inspect CRX | Refuses installation with `CRX_SIGNATURE_UNVERIFIED`, including a CRX renamed to ZIP. No header stripping or signature bypass. |
| Accept installation | Requires the preview token, explicit permission acceptance and at least one selected existing identity. The accepted copied tree is hashed again. File access defaults off and requires a separate boolean choice. Changed preview bytes cannot reuse consent. |
| Own package | Moves the approved copy to `extensions/packages/<stable UUID>`. Files and directory entries are flushed before registry commitment. The original source may change or disappear without changing the installed package. |
| Enable / disable | Persists explicit per-identity intent. Enabling uses `session.extensions.loadExtension` and waits for a persistent MV2 background document to finish loading when one is declared; disabling uses `removeExtension` and checks `getExtension`. Failed readiness removes the newly loaded runtime. A failed unload is visibly `disable-failed`, with an explicit possibly-still-running error; re-enabling or receiving a registration event cannot relabel that failure as success. |
| Restart | Validates owned package bytes against consent before reloading. The stable owned path preserves the runtime extension identity across restarts. A disabled identity is not loaded. |
| Additional identity | Requires a new explicit acceptance through `authorizeIdentity`; extensions never enroll another identity automatically. Each identity uses its own persistent Electron session and extension storage. |
| Popup / options | `pageFor` accepts only a declared approved local page in a currently loaded, authorized identity. The result must stay in the loaded extension's own `chrome-extension://` host. The browser owns secure window construction and closes these hosts before disabling/uninstalling. |
| Uninstall | Persists disabled intent, unloads each running identity, removes owned package code, then removes the record. Failed unloading or file removal leaves a retryable record. Existing Chromium extension storage is explicitly retained; data erasure is not claimed. |
| Recovery | Malformed, duplicate-key, newer-schema and externally changed registries are not silently replaced. A missing primary with an existing checkpoint requires explicit recovery. An invalid previous checkpoint is preserved. A rename acknowledged with an I/O failure does not cause package rollback beneath a visible registry record. |

Preview acceptance is tied to owned bytes, not to a mutable source path. Packages with the same digest or explicit publisher identity are not installed as competing runtime instances. No arbitrary extension-count or file-count limit is imposed. Windows-ambiguous names, encrypted archives, links and special files are explicit unsupported inputs rather than silently altered packages.

### Startup and activity

`open()` reads metadata only. The desktop shell uses `restoreIdentity(identity)` before loading that identity's first page. Other inactive identities are not initialized implicitly. An explicit install/enable starts the selected identity immediately; `restore()` remains available when all authorized identities should be restored. Repeated restoration recognizes already-loaded instances and does not repeat their disk verification or `loadExtension` call.

There are no manager polling timers or extension monitoring workers. Native load/unload notifications update runtime presence; registration alone cannot assert readiness. Persistent MV2 startup temporarily observes native background contexts and has one 15-second failure deadline after native registration. This is an event-driven readiness check, with no repeated loads or fixed startup delay. All temporary listeners and the deadline are removed after success or failure. Lazy MV2, MV3, and content-only packages retain the native loader's completion semantics.

Disabled extensions have no manager-started runtime; verifying termination of actual background pages/service workers, and the behavior of content scripts already injected into an existing document, requires the separate native fixture. Disabling does not undo an extension's prior DOM changes. Reloading a page is a distinct user action.

### API used by the shell

```js
const {createExtensionLoader} = require('./extension-runtime.cjs');
const {createExtensionBridge} = require('./extension-bridge.cjs');
const manager = new ExtensionManager({
  directory: path.join(userData, 'extensions'),
  getSession: identitySession,
  getIdentities: () => profiles.map(profile => profile.id),
  loadExtension: createExtensionLoader({app, webContents}),
});
await manager.open();
const bridge = createExtensionBridge({ipcMain, manager, host: extensionHost()});
// identitySession() calls bridge.attachSession(nativeSession) before every load.
await manager.restoreIdentity(activeIdentity);

const preview = await manager.preview(userSelectedAbsolutePath);
const item = await manager.install(preview.token, {
  identities: selectedIdentities,
  permissionsAccepted: true,
  allowFileAccess: false,
  unsignedImportAccepted: explicitUnsignedImportConsent,
});
await manager.setEnabled(item.id, activeIdentity, false);
await manager.authorizeIdentity(item.id, anotherIdentity, {
  permissionsAccepted: true,
  allowFileAccess: false,
});
const optionsURL = manager.pageFor(item.id, anotherIdentity, 'options');
const snapshot = manager.list();
await manager.uninstall(item.id);
await bridge.dispose();
await manager.dispose();
```

The acceptance flags in this example must come from actual user review, not automatic approval. `list()` separates `enabled` intent from `status`, `runtimeId`, and `error` for every identity. `loaded` means the engine confirmed loading and, for a persistent MV2 background, its initial document completed. It does not promise completion of asynchronous extension initialization or establish API compatibility. `compatibility.functionalVerification` remains `not-tested`; a synthetic package passing a native fixture does not prove every extension with similar permissions will function.

## Authenticated browser-host API integration

The current continuation adds `extension-bridge.cjs`, `extension-policy.cjs`, `extension-menus.cjs`, `extension-icons.cjs` and `extension-api.preload.cjs`. The maintained Electron adapter supplied reusable context-menu selection/title rules and an isolated-to-main-world transport design; the insecure principal routing and success-shaped methods identified below were not imported. The browser services remain canonical: tabs and the actual window come from the shell, cookies from the exact native identity Session, and bookmarks/history from their durable services. There is no second extension-only bookmark or history database.

### Principal, grant and lifecycle boundaries

Every request authenticates the native `senderFrame`'s committed `chrome-extension://` URL and actual Session, or the actual native worker object/version/Session. The host resolves that runtime ID to the manager's verified owned package path and enabled identity grant. Caller-supplied extension IDs, identity names, remote sessions or secret tokens are not authority. Granted host patterns and required permissions come from the loaded manifest after package verification, not mutable display metadata in the registry. Optional manifest permissions are displayed but never promoted into accepted host grants.

Authorization is available during a verified managed load so real background startup can call host APIs. Each load has a distinct enrollment epoch. Disabling, failed loading, native unloading or uninstall revokes that epoch before cleanup; failed native removal remains visibly `disable-failed` while browser-host calls and events stay revoked. An old native context cannot borrow a new enrollment after re-enable. Asynchronous replies recheck both the epoch and committed caller origin, so navigation during a cookie read cannot deliver the result to a website. Main-process `host.runOperation` admission covers dispatch through the final check and participates in normal shutdown draining.

The Session preload is limited to actual extension URLs, with origin fallback disabled. Ordinary webpages, content scripts in web-frame worlds, initial empty frames, blob URLs and about pages do not receive this added transport. Native content-script messaging remains native. Expanded content-context APIs require a separate authenticated principal mechanism and are **not** claimed. Frame/worker listeners use weak references and are removed on revocation, worker stop and disposal. No background keepalive, poller, hidden host, worker wake shim or replay queue was added.

Native MV2 background pages and isolated extension windows do not use the same JavaScript context arrangement. The preload checks Electron's actual `process.contextIsolated`: isolated windows transfer the facade through `contextBridge`; native background pages initialize that same facade directly in their existing context with a closure-private transport. This follows the maintained adapter's context routing. It does not change the sandbox, Node integration, context-isolation preferences or the main-process authentication rules. A website fails the URL guard before either path exposes any transport.

`addListener`/`removeListener` use a separate synchronous, authenticated route that only changes in-memory weak subscriptions. Registration is complete when `addListener` returns; the first host event cannot overtake an asynchronous registration request. The other synchronous route performs browser/native tab-ID metadata lookups only. Neither path performs disk work, starts a view, waits for a service or mutates user data. A runtime context lacking the required synchronous transport fails explicitly. Service methods remain asynchronous IPC.

### Permission queries from the accepted enrollment

The first actual unchanged Dark Reader 4.9.135 Windows run at `f76e79d96790d104573cb55cd0b666467da9f4b7` installed the reviewed original ZIP and reached its persistent background document, then recorded `chrome.permissions` as missing through the package's `background/index.js:6356` exception while accessing `onRemoved`. The separate [real-package workflow](https://github.com/Herbertofury/Noxviola/actions/runs/43780643491) did not darken the page. Native alarms registration occurred earlier without that exception, so this repair does not replace native alarms or infer other missing APIs. The unchanged package and original failure artifacts remain the next acceptance test.

The added namespace performs real read-only queries. The principal and post-dispatch checks are exactly those used by other browser-host APIs; neither a request payload nor an old document can choose another identity or reuse a revoked enrollment. `contains` requires every named permission and requested origin to be covered by accepted grants. Optional API/host declarations alone return false. Required API names are reported as grants, independently of whether their implementation is available. Chrome callback results/errors and the unchanged Mozilla Promise facade both use the authenticated transport.

MV2 host entries in `permissions` and MV3 `host_permissions` become origins, with host-permission paths normalized to `/*`. Accepted `content_scripts.matches` are included as scriptable origins while retaining their paths; this does not promote them into cookie or tab-metadata grants. When a query also matches a declared optional explicit host, Chromium's explicit/scriptable classification requires that optional grant too: a scriptable-only match cannot substitute for it. Required explicit coverage takes precedence over an overlapping optional declaration. Coverage requires complete scheme and domain containment, including wildcard subdomains. Scriptable paths use full wildcard-language inclusion rather than matching a sample path or stripping a wildcard. Literal near misses use the same nonbacktracking automaton; valid patterns are not truncated or capped. Explicit file-origin queries require the separate accepted file-access setting. `<all_urls>` retains the standard spelling, but it does not bypass that setting. HTTP, HTTPS, FTP, file, wildcard HTTP(S) and `<all_urls>` patterns are supported; unsupported pattern forms, structured permission arguments and Firefox data-collection query fields reject explicitly. This subset uses the Chromium grant-set model; selecting the Firefox behavior profile does not assert complete Firefox permissions equivalence.

The intended query semantics are informed by [Chrome permissions](https://developer.chrome.com/docs/extensions/reference/api/permissions), [Firefox contains](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/permissions/contains), [Firefox getAll](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/permissions/getAll), and Chromium 152's [permission API](https://github.com/chromium/chromium/blob/152.0.7977.169/chrome/browser/extensions/api/permissions/permissions_api.cc) and [explicit/scriptable permission handling](https://github.com/chromium/chromium/blob/152.0.7977.169/chrome/browser/extensions/api/permissions/permissions_api_helpers.cc). Noxviola omits unapproved explicit file origins from `getAll`; the pinned Chrome implementation documents a remaining file-origin filtering TODO. No optional-grant store or grant-change event is fabricated. Real request/removal needs user-gesture admission, reviewed consent, durable scopes and matching native enforcement before those methods can be promoted.

### Host integration and packaging contract

`createExtensionBridge({ipcMain, manager, host, nativeImage})` returns `attachSession`, `contextMenuItems(identity, tabId, nativeParams)`, `actionState(identity, tabId)`, `activateAction(identity, runtimeId, tabId)` and `dispose`. Production passes Electron's actual `nativeImage` export for verified PNG decoding. Attach each exact Session **before** native extension loading. Registering the bridge does not enroll any new identity.

The host supplies identity-first `tabs.list/get/create/update/remove/move/reload`, synchronous `tabs.nativeId/browserId` mappings, `windows.getCurrent/getAll/update`, the canonical `bookmarks` and `history` objects, `{identity,event,args}` subscriptions, `actionsChanged`, a same-loaded-origin `openExtensionPage`, and `runOperation(work)` for close admission/draining. Tab descriptors include internal `identity` so the bridge can verify and strip it. `windows` receives the requested `{populate}` option. The host must not create native contents merely to enumerate metadata.

Runtime packaging must retain the five new modules and both `extension-adapter-LICENSE.txt` and `extension-browser-polyfill-LICENSE.txt`, alongside the existing manager and readiness loader. The Mozilla distribution is embedded in the single extension preload to avoid runtime filesystem imports/evaluation in a sandboxed preload. The portable test hashes the exact embedded bytes. No new runtime dependency or native sandbox exception is required.

### Action icon bytes, defaults and lifetime

Package inspection already hashes each file. The manager now retains those hashes and sizes in a private in-memory inventory tied to the accepted load epoch; they are never taken from renderer input or persisted as editable registry authority. `readRuntimeResource(context, resourcePath)` requires an exact inventory entry and current enrollment, rejects linked/replaced directories and nonregular files, opens with the platform's available no-follow/nonblocking flags, checks file/ancestor identities and stable read metadata, compares the actual bytes against the accepted SHA-256, and checks enrollment again. No package bytes are rewritten.

The preload resolves caller paths against the actual document base and transfers ImageData as a stable copied RGBA array with explicit dimensions. Main accepts only the authenticated extension origin and its verified resource inventory. A path can never select a website, another extension, a data URL or arbitrary host file. PNG chunks, checksums and dimensions are validated before the real native decoder; the decoded image is re-encoded to PNG. ImageData uses a small RGBA PNG encoder with asynchronous zlib compression, avoiding Electron's platform-dependent raw bitmap format. Dimensions use Chromium's checked signed-integer RGBA bound, with exact byte length required. No remote fetch, image worker, timer or keepalive is introduced.

`actionState.icon` is `null` or `{variants:[{size,width,height,dataUrl}]}`. Declared sizes and actual bitmap dimensions are both retained; the shell displays a logical 16-pixel image with size-based density candidates and keeps the action name, accessible title and badge. Only host-produced `data:image/png;base64,` images reach this path. A default-icon failure provides a real `iconError`; the readable name remains visible. An explicit setter failure rejects and preserves the previous icon.

Manifest icons decode once per action enrollment; repeated resource reads/decodes share an epoch-bound cache. Per-tab icons override global icons, which override the manifest default. Scalar inputs declare logical size 16, separately retaining their actual bitmap dimensions, following the current [Chrome action contract](https://developer.chrome.com/docs/extensions/reference/api/action#method-setIcon). When both forms exist, ImageData takes precedence, matching the [pinned Chromium implementation](https://github.com/chromium/chromium/blob/152.0.7977.169/extensions/renderer/resources/set_icon.js) and the observed Violentmonkey call. Static PNG and 8-bit sRGB are the current supported image subset. SVG/animated images and wide-gamut/float formats remain open.

The reviewed install choice `apiProfile: 'chromium' | 'firefox'` controls implemented semantic differences. It is persisted by the manager and captured for each enrollment, never read from individual API calls or inferred from use of the `browser` namespace. Legacy/missing choices use Chromium behavior. Preview `apiProfileSuggestion` offers Firefox for XPI and Chromium otherwise, but that is an advisory format hint; users can correct it. Cross-browser manifests and renamed archives do not establish a trusted ecosystem. Choosing a behavior profile neither authenticates a publisher nor widens grants, host patterns or any engine setting.

In the Chromium profile, empty icon setters reject and tab icons survive navigation until closure or another explicit update. In the Firefox profile, null/empty forms clear the relevant override, and a genuine full-document tab commit clears that tab's icon; same-document commits and title/loading changes do not. A main-only `tab-navigation-committed` event identifies the actual tab and document transition. It also invalidates an older pending tab-icon decode so that stale work cannot restore the cleared override. These differences follow the [Chrome](https://developer.chrome.com/docs/extensions/reference/api/action#method-setIcon) and [Firefox](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/action/setIcon) references; this is a limited explicit profile, not engine equivalence. Window-specific icon settings still reject.

Concurrent image preparation does not serialize unrelated work. A late earlier result cannot overwrite a newer successful update/reset; a failed later update does not discard an earlier valid result. Before any asynchronous image is applied, the host revalidates the actual sender origin, enrollment and target tab. Revocation, tab closure and disposal release action overrides and owned caches. These contracts are covered in portable tests; native decoder and visible pixel acceptance are separate gates.

The [45.0 breaking-change review](https://github.com/electron/electron/blob/v45.3.2/docs/breaking-changes.md) found no required weakening of Noxviola's sandbox or permissions:
